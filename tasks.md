- [x] Stripe webhook controller no longer swallows transient failures as permanent ones (2026-08-09): `StripeWebhookController.handleWebhook` caught every error from `handleEvent` uniformly and always acked 200 — meaning a dropped DB connection during payment processing looked identical to a genuinely permanent `INVALID_STATE_TRANSITION` rejection, and both got silently swallowed with no path to reconciliation. Since Stripe retries on any non-2xx for up to 3 days, that swallowing was actively throwing away the retry safety net for exactly the failures that needed it most. Fixed by narrowing the catch to only ack-and-suppress `ConflictException` (confirmed via `assertTransition` — the only exception type this call chain can actually throw for a reason retrying won't fix); everything else now rethrows, hits the global exception filter's default 500 fallback, and gets retried by Stripe like it should. Updated the existing controller spec that had explicitly locked in the old swallow-everything behavior, and added the missing negative case (non-ConflictException rethrows). DocuSeal's and Clerk's webhook controllers already did this correctly (no blanket catch — errors propagate to the filter by default), so this was Stripe-specific. 338/338 tests pass (1 new); tsc/eslint/nest build clean.

- [x] Webhook idempotency review (2026-08-09): audited all three webhook integrations (Stripe, DocuSeal, Clerk) for duplicate-delivery and replay handling.
